Explicacao para Nao-Tecnicos

Entendendo sem precisar ser programador
💡 A ANALOGIA DO OPERADOR DE FABRICA

Pense no QA Flash como um operador de fabrica que sabe operar varias maquinas. Ele nao importa qual maquina voce coloque na frente dele - ele se adapta e trabalha.

Plataforma

Explicacao leiga: E o tipo de maquina onde o robo trabalha.

Exemplos: Navegador (site), Celular (app), Terminal verde (banco), API (sistema interno)

Linguagem

Explicacao leiga: E o idioma que o robo fala para comandar a maquina.

Exemplos: Java (empresas), Python (simples), TypeScript (frontend), Ruby (legado)

Framework

Explicacao leiga: E a ferramenta que o robo segura para operar.

Exemplos: Selenium (classico), Cypress (moderno), Playwright (rapido), Appium (celular)

BDD

Explicacao leiga: E a lingua que todo mundo entende - do estagiario ao diretor.

Formato: Dado (preparar), Quando (executar), Entao (validar)

Resumo: O QA escolhe 3 coisas (Plataforma + Linguagem + Framework) e o robo gera o codigo pronto. As regras de qualidade sao sempre as mesmas, independente da escolha.

Plataforma API (Postman)

Testar endpoints REST - manual e automatizado
EXPLICACAO LEIGA

E como o robo liga para outro sistema e verifica se a resposta esta correta. Em vez de clicar na tela, ele envia um pedido (requisicao) e checa se a resposta (status, dados) esta certa.

Modo MANUAL (QA confere)

1. Robo gera Collection .json do Postman

2. QA importa no Postman

3. QA clica em "Send"

4. QA confere o resultado na tela

5. QA aprova ou reprova

Para que serve: Explorar, debugar, entender a API

Modo AUTOMATIZADO (CI/CD)

1. Robo gera scripts de teste

2. Newman roda no CI/CD

3. Resultado automatico

4. Relatorio gerado sozinho

5. QA revisa o relatorio

Para que serve: Regressao continua, pipeline

O Que Nao Muda em Nenhuma Combinacao

A base de qualidade que e sempre igual
EXPLICACAO LEIGA

Independente da linguagem ou framework escolhido, estas regras sao sempre iguais. E o que garante qualidade em qualquer projeto, seja Web, Mobile, API ou Mainframe.

BDD (Gherkin)

Dado, Quando, Entao - sempre em portugues, sempre igual. O diretor e o estagiario entendem a mesma coisa.

Padrao AAA

Arrange (Preparar), Act (Executar), Assert (Validar). Estrutura clara em todos os testes.

Page Object Model

Separar o mapeamento de tela do codigo de teste. Se a tela muda, so atualiza um arquivo.

Principios FIRST

Rapido, Independente, Repetivel, Autovailidado, Oportuno. Cada teste roda sozinho.

Locators Resilientes

Web: data-testid. Mobile: accessibility-id. Mainframe: linha+coluna. Nunca XPath absoluto.

Esperas Dinamicas

Nunca usar pausa fixa (Thread.sleep, cy.wait). Sempre esperar o elemento aparecer.

Seguranca

Credenciais sempre em .env, nunca em texto puro. Compliance OWASP e LGPD.

Human-in-the-Loop

4 paradas obrigatorias. O QA humano decide em cada uma. O robo nunca avanca sozinho.

Mesmo Teste, 3 Frameworks Diferentes

O BDD nao muda, so muda o codigo por tras
EXPLICACAO LEIGA

O mesmo cenario de teste escrito em 3 frameworks diferentes. Repare que a logica e a mesma - so muda a forma de escrever o codigo, como falar a mesma frase em 3 idiomas diferentes.

O cenario BDD (igual para todos)

Dado que estou na pagina de login Quando preencho o e-mail e clico em entrar Entao o dashboard deve aparecer

Selenium (Java)

driver.findElement(By.cssSelector( "[data-testid='email']")) .sendKeys("user@test.com"); driver.findElement(By.cssSelector( "[data-testid='btn-entrar']")) .click(); wait.until(ExpectedConditions .visibilityOfElementLocated( By.cssSelector("[data-testid='dashboard']")));

Cypress (TypeScript)

cy.get('[data-testid="email"]') .type('user@test.com'); cy.get('[data-testid="btn-entrar"]') .click(); cy.get('[data-testid="dashboard"]') .should('be.visible');

Playwright (TypeScript)

await page.fill('[data-testid="email"]', 'user@test.com'); await page.click('[data-testid="btn-entrar"]'); await page.waitForSelector('[data-testid="dashboard"]', { state: 'visible' });
